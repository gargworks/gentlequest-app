## W1 and W2 RUN CONCURRENTLY — this is not a sequence

Stated explicitly because review caught the first draft implying otherwise:
**acquisition (W2) does not wait for the cohort audit (W1).** Whichever way W1
resolves, more real native users are required — if the cohort is contaminated
we need real ones to replace the noise, and if it is clean we still need n to
hold up under exclusion. W1 is higher-priority for *correctness of the verdict*;
W2 is the only thing that changes the *outcome*. Do not serialise them.

## W1 — THE COHORT IS CONTAMINATED (correctness of the verdict)

Measured today, GA4 property 551876340, `first_open`, window start → now:

```
Android 28 + iOS 16 = 44 native installs   → n>=40 already "met"
```

**That number is not trustworthy.** Android appVersion 1.7.3 alone is 15 users,
and essentially all of them are my emulator runs from 2026-09-03/04 (repeated
`pm clear` + reinstall each mints a new install). The operator's own device
testing adds more.

So the gate's n≥40 may already read as PASSED on a cohort made largely of
**our own testing**. A D14 verdict computed on that population is fiction — and
it would be a *favourable* fiction, which is the dangerous direction.

**Do first:**
1. Quantify internal installs inside the window. Segment `first_open` by
   appVersion and platform; treat 1.7.3 Android as suspect-by-default and
   confirm against the dates I ran the emulator.
2. Decide the exclusion rule and **write it into ADR-007 as an amendment** —
   the population definition is ratified text and cannot be narrowed silently.
   GA4 has no internal-traffic filter configured; that is the mechanism to add.
3. Re-derive the honest eligible n. If it is <40, say so plainly; the gate then
   depends on real acquisition, not on a number we manufactured.

**Definition of done:** eligible-n stated with the exclusion rule ratified, and
every install in the window assigned to exactly one bucket (real / internal /
unknown), with unknown ≤ 10%.

**Delegatable:** the segmentation and counting, yes. The ADR amendment, no.

## W3 — Reconcile the instruments (BOUNDED side task, not a blocker)

The 5x was inflated, but a real question survives: `all_time: 51` IS a distinct
count (`all_sessions ... .distinct()`), and the true 7-day unique figure is
bounded by `max(daily)=6 ≤ true ≤ 19` against GA4's 4. Still worth closing, and
a lane is already investigating.

Sharper bar than v1's hand-wavy "~20%", taken from the review:
- one frozen UTC interval, one population;
- backend recomputed as **distinct sessions across the whole interval**, not a
  sum of daily buckets;
- every backend session in exactly one bucket: native-with-GA4-event / native
  anonymity-mode / web / internal / unknown / failed-send;
- unknown ≤ max(1, 10%);
- compare GA4 only against the native bucket.

Also note, and it blocks naive reconciliation: `first_chat_message_sent` fires
*before* the network call (`chat_provider.dart:341-362`), so it means "send
attempted", not "message stored". The two are not the same event.

### RESOLVED 2026-09-05 — the two metrics are STRUCTURALLY non-comparable

A glm-5-2 lane investigated and I verified its structural claims directly:

- **`Message` has no platform column.** Columns are exactly: id, session_id,
  content, is_user, timestamp, risk_level, resources, message_type
  (`models.py`). No platform, no user_agent.
- **`AnalyticsEvent` has no platform column either.** The lane asserted it did
  and built its recommended reconciliation query on that join — I checked, and
  the join it proposed cannot run. Its verdict was right; its remedy was not.

**So there is NO query that segments backend chat sessions by platform.** The
backend number is all-platforms-blended by construction; the GA4 number is
native-only by ADR-007 construction. They cannot be reconciled, now or later,
without a schema change.

Compounding inflation, both CERTAIN:
- `/api/chat` calls `_get_or_create_session()` (`routes/chat.py:44`), which
  mints a fresh uuid4 whenever `X-Session-ID` is absent. Any non-Flutter caller
  — curl, bot, my own smoke tests — creates ONE SESSION PER MESSAGE.
- The blocklist is a hand-maintained JSON of 7 UUIDs
  (`config/test_session_blocklist.json`), of which 1 has ever matched. Nothing
  automatic excludes test traffic.

**Ruling: `/api/metrics/true` must not be used to support any claim about
native users, or compared to the GA4 funnel.** It is a legitimate all-platform
liveness signal and nothing more. Either add a platform column to `Message` and
populate it, or stop treating these as two views of one thing.

That also retires the "5x contradiction" entirely: it was one unit error (mine)
on top of a comparison that was never valid.

## Standing constraints (learned, not theoretical)

- Pass `--min-version` to the funnel or conversions exceed 100%.
- Bump the version NAME, not just the build number, when shipping a funnel
  stage — appVersion is the name, so 1.7.3 spans builds with and without the
  vow events.
- **Never sum a per-day trend and call it a unique count.** That is what
  produced v1's headline error.
- Never read one instrument's silence as absence.
- Positive control on every guard; opposed pair on every claim.
