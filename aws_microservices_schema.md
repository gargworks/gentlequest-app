# Hypothetical AWS Microservices Schema

To facilitate the CODE RED migration simulation, a representative set of 100 hypothetical AWS microservices needs to be analyzed. Below is the schema defining the characteristics for each microservice, which will guide the migration planning to Google Cloud Run.

## Microservice Attributes:

1.  **`service_id`**: (String) Unique identifier for the microservice. (e.g., `order-processing-service-001`)
2.  **`programming_language`**: (String) The primary language the microservice is written in. (e.g., `Python`, `Node.js`, `Java`, `Go`, `Ruby`)
3.  **`runtime_environment`**: (String) The current AWS compute environment where the microservice runs. (e.g., `Lambda`, `EC2`, `Fargate`, `ECS`, `EKS`)
4.  **`containerized`**: (Boolean) Indicates if the microservice is already running in a container. (`true`/`false`)
5.  **`stateless`**: (Boolean) Indicates if the microservice is stateless. This is crucial for Cloud Run compatibility. (`true`/`false`)
6.  **`primary_data_store`**: (String) The primary data storage service used by the microservice. (e.g., `RDS PostgreSQL`, `RDS MySQL`, `DynamoDB`, `S3`, `ElastiCache Redis`, `DocumentDB`)
7.  **`other_aws_integrations`**: (Array of Strings) A list of other AWS services the microservice integrates with. (e.g., `SQS`, `SNS`, `API Gateway`, `Secrets Manager`, `CloudWatch`, `KMS`, `Cognito`, `Step Functions`, `AppSync`)
8.  **`api_endpoints_count`**: (Integer) Number of API endpoints exposed by the microservice. (e.g., `1`, `5`, `10`)
9.  **`internal_dependencies_count`**: (Integer) Number of other internal microservices this microservice depends on. (e.g., `0`, `2`, `7`)
10. **`external_dependencies_count`**: (Integer) Number of external (non-AWS, non-internal microservice) services this microservice depends on. (e.g., `0`, `1`, `3`)

## Generation Approach for 100 Microservices:

To create a diverse and realistic dataset, the 100 microservices will be generated by varying the above attributes. The distribution of values will aim to reflect a typical enterprise environment, including a mix of:

*   **Languages**: Predominantly Python, Node.js, Java, with some Go and Ruby.
*   **Runtime Environments**: A good mix of Lambda (requiring containerization for Cloud Run), EC2 (straightforward containerization), and Fargate/ECS/EKS (already containerized).
*   **Containerization Status**: A mix of already containerized services and those that will need containerization.
*   **Statelessness**: A critical attribute, with a bias towards stateless for easier Cloud Run migration, but also including stateful services to highlight migration challenges for data stores.
*   **Data Stores**: A variety including relational (RDS), NoSQL (DynamoDB), object storage (S3), and caching (ElastiCache).
*   **AWS Integrations**: A rich set of integrations to simulate real-world complexity, focusing on services that have direct GCP equivalents or require re-architecting.
*   **Dependency Counts**: Varying levels of dependencies to identify services that are more coupled or more isolated.

This schema and generation approach will serve as the basis for the detailed analysis phase, providing the necessary input for subsequent design, IAC, CI/CD, migration, and validation efforts.
